# ArkPkg v1 与原生包管理器

ArkOS 0.12.0 支持将原生 SDK 应用打包为 `.arkpkg`，在客体中检查、安装、升级、撤销权限、启动和卸载。图形入口在 Dock 和启动台，名称为“包管理器”；文件管理器打开 `.arkpkg` 会进入包检查界面。终端提供 `pkg` 命令。

安装包与应用在 ArkOS 内执行；宿主 Python 工具只在开发时生成包。内核共用原有 ELF 检查，执行文件仍进入独立 Ring3 页表，保持 W^X/NX、用户栈不可执行、每进程资源上限和真实 UID 权限检查。

## 创建包

从源码根目录执行：

```sh
sh sdk/build-app.sh sdk/hello.c build/hello.elf
python3 scripts/arkpkg.py build build/hello.elf build/hello.arkpkg \
  --id hello --title "Hello ArkOS" --version 1.0.0 \
  --summary "示例应用" --permissions ui,files
python3 scripts/arkpkg.py inspect build/hello.arkpkg
```

工具只依赖 Python 标准库。它保留 ELF 入口、虚拟地址、段权限和加载字节，去掉运行时不需要的符号与节表，并压紧文件偏移。应用需要的只读图片、字库和其他资源可以链接在 ELF 内。

将包放入客体可读取的 FAT32/NTFS 外置卷，或当前账号的二进制对象区。随附 `workspace-0.13.0.arkpkg` 来自完整的 `sdk/workspace.c`，实际创建多个窗口并接受文字拖放。`sdk/hello.c` 可用于自行构建安装与升级示例。

## 客体操作

```text
pkg info /mnt/fat32/hello.arkpkg
pkg install /mnt/fat32/hello.arkpkg
pkg list
pkg run hello
pkg grant hello 6
pkg upgrade /mnt/fat32/hello-new.arkpkg
pkg remove hello
```

`pkg info/install/upgrade` 也接受 `blob:文件名`。相对文件路径按终端当前目录解析。`pkg run ID [argument]` 显示独立窗口；`run pkg.ID [argument]` 可直接调用原生启动接口。包应用也会出现在启动台中。运行中的应用需先关闭，才能升级或卸载；用户文档保留在原有账号目录。

首次安装只授予 UI=4。FILES=2、NETWORK=8、ACTIVITY=32 在图形界面中分别授权，或使用十进制 `pkg grant ID MASK` 设置；例如 6 表示 UI+FILES。包声明限制最高可授予范围。升级保留已有授权与新版本声明的交集，新增权限由用户再授予。内置十一个应用的授权记录继续使用原有稳定 ID，安装包使用独立的运行时目录槽和授权 ID。

## 二进制布局

所有整数为小端，包为 256 字节清单与一个完整静态 ELF64 载荷。

| 偏移 | 长度 | 内容 |
|---:|---:|---|
| 0 | 8 | `ARKPKG1` 加 NUL |
| 8 | 2 | 格式版本 1 |
| 10 | 2 | 架构 62，x86-64 |
| 12 | 4 | 清单长度 256 |
| 16 | 4 | 包总字节数 |
| 20 | 4 | ArkOS ABI 1 |
| 24 | 4 | 声明的最大权限，必须包含 UI，范围为 46 的子集 |
| 28、32、36 | 各 4 | 主、次、修订版本，无符号整数 |
| 40 | 4 | ELF 载荷字节数，等于总长度减 256 |
| 44 | 4 | 普通磁盘安装包 flags=0；启动镜像内系统包使用受信任的入口标志 |
| 48 | 32 | NUL 结尾 ID，1–27 个小写 ASCII 字母、数字、点、连字符；首字符为字母或数字，末字符不能为点 |
| 80 | 64 | NUL 结尾 UTF-8 名称 |
| 144 | 64 | NUL 结尾 UTF-8 简介 |
| 208 | 32 | ELF 载荷 SHA-256 |
| 240 | 12 | 保留字节，固定 0 |
| 252 | 4 | 前 252 字节的 CRC-32 |
| 256 | 剩余字节 | 原生静态 ELF64 |

版本按主、次、修订三个数字依次比较。升级必须保持 ID，并严格增加版本。加载器拒绝动态链接、TLS、执行栈、RWX 段、重叠段、非法入口、越界布局及超过 64 MiB 的普通进程映射预算。

## 持久化与边界

安装数据存入 ArkFS 二进制区的 `@pkg.ID` 私有对象。普通 BLOB 调用既不能枚举，也不能读写这些对象，SYSTEM 桌面的公开 BLOB 接口同样受此限制。内核内部接口从真实会话取得 UID，调用者无法选择其他账号。

32 字节安装封套记录 `ARKINST1`、稳定槽号、已授权权限及包长度。封套与整个包作为同一对象写入，沿用双代 CRC 索引、写时复制与 flush 提交。失败保留上一代记录。每次启动重新检查磁盘对象 CRC、清单、载荷 SHA-256 和 ELF；图形安装还绑定检查时清单的 SHA-256，源文件改变时要求重新读取。

首版支持本地单 ELF 应用包。在线仓库、依赖求解、压缩载荷、发布者签名及安装脚本尚未接入；SHA-256 用于完整性检查，不能证明发布者身份。图形界面会显示“发布者未签名”。包应用通过包管理器显式申请文件、网络和活动权限，内置应用继续使用原有可信授权弹窗。

包与二进制对象索引按需增长，容量由磁盘空间、COW 备用空间和 4 MiB 元数据内存决定。单包最多 `8 MiB−32` 字节，更新需要额外的写时复制空间。任务上限 32、surface 上限 12；独立 surface 最大 3840×2160，SDK 常用逻辑内容 800×500；高分辨率自动 2 倍绘制。QEMU 推荐 512 MiB 与 4 个 CPU。包架构当前为 x86-64，ARM64 不在此包格式的客体验收范围。

## 验证

`make check-package-host` 使用真实包、ELF、SHA-256 和二进制事务模块，检查摘要向量、外置索引、损坏载荷、RWX、权限上限、检查后源文件改变、升级授权保留、提交失败恢复、账号隔离及持久化删除。`tests/package_count_vm_test.py` 在真实客体安装 48 个小型可执行测试包，重启检查稳定槽号与授权、独立解码两个 ARKIDX2 页面，并用生产桌面显示共 65 个应用。`tests/desktop_011_test.py bios/uefi` 验证 17 个系统包与实际启动。结果保存在各次测试的输出目录。

## 系统应用包

构建生成 `build/packages/ark.*.arkpkg`，共 19 个实际容器；均含清单、SHA-256 和可加载 ELF。十一个独立应用使用各自 Ring3 ELF。终端、文件、设置、关于、任务、录制、安装器和包管理器使用同一可信桌面 ELF，清单标志 `2 | (desktop_id << 8)` 指定入口；独立系统包标志为 1。它们并非 19 个相互隔离的进程。

系统包由不可变启动镜像提供，内核在启动时验证清单、载荷摘要与 ELF，再按包启动程序。LIST 前 19 项返回 `installed=2`、slot=桌面入口；随后是当前用户 `installed=1` 的包。磁盘安装接口拒绝系统标志及 SYSTEM/PROCESS 权限，也禁止覆盖系统 ID。系统包随系统镜像更新，普通包由管理器单独安装、升级、授权和卸载。

LIST 使用稠密枚举序号，遇到 -2 结束；序号与稳定 slot 不是同一字段。FIND=6 按 ID 查询，权限 ID 为 `256+slot`，桌面 ID 为 `19+slot`。应用卸载后新安装可复用空闲 slot；其他包的授权不变。

持久化 ARKBLOB2 使用两个 4 KiB 根（LBA 8192/8200）和可增长链式 ARKIDX2 页面，每页最多 42 条记录。单页条数是磁盘布局单位，不是对象总量限制。旧 ARKBLOB1 仍可读取；下一次成功提交写入新布局，失败保留旧代数与有效数据。没有文本文件迁移或用户数据清空。

## 0.12.0 窗口与运行中包

SPAWN 的 `ARK_SPAWN_NEW=1` 为普通包和目录应用启动新进程；flags=0 激活已有实例。每个进程可拥有多个 surface，系统总上限仍为 12。关闭一个 surface 保留其他窗口，关闭最后一个才退出。最小化保留进程和窗口，恢复时复制其最新内容。

升级与卸载检查该包当前 UID 的全部存活实例，不能只检查最近的 PID。任何实例仍在运行时返回 -16。主机包测试覆盖两个实际模型 PID、独立启动参数及关闭其中一个后仍拒绝卸载；真实 SDK 多 surface 由 `tests/lifecycle_013_test.py` 检查，记录保存在各次测试输出目录。

十九个系统包含日历与提醒事项。包含词典的可信桌面 ELF 使用 SYSTEM 预算；普通磁盘包仍受 `8 MiB−32` 总长度限制，不能声明可信系统标志。
